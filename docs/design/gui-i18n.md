# Design: English and Korean GUI, with README screenshots

Status: v1, ready for implementation.

## Problem

Every GUI text is hard-coded Korean. The text sits in these places:
- the renderer: `gui/src/renderer/app.ts` (about 157 lines), `gui/src/renderer/admin.ts` (about 89) and `gui/src/renderer/index.html` (about 15);
- the main process: `gui/src/main/main.ts` (native dialogs, about 15);
- the admin session's messages: `gui/src/service/admin.ts` (about 28);
- `gui/src/service/types.ts` (1).

English-speaking users cannot use the GUI. The README also has no picture of it.

Phase 2 will add about 40 more texts. It will add each one to the catalog below in both languages.

## Decisions

### 1. One message catalog

- **The catalog file.** `gui/src/i18n/messages.ts` is new.
  - It is compiled by both `tsconfig.build.json` (main and service) and `tsconfig.renderer.json` (renderer). Add `src/i18n/**/*.ts` to both `include` lists, and to `tsconfig.json`.
  - It imports nothing, so the renderer can load it.
- **Exports.**

  ```ts
  export type Lang = 'ko' | 'en';
  export const LANGS: readonly Lang[] = ['ko', 'en'];
  export const MESSAGES = { ko: { … }, en: { … } } as const;   // same keys in both
  export type MessageKey = keyof typeof MESSAGES.ko;
  export function t(lang: Lang, key: MessageKey, params?: Record<string, string | number>): string;
  export function langFromLocale(locale: string | undefined): Lang; // 'ko' or a 'ko-…' locale gives 'ko', anything else gives 'en'
  ```
- **`t` behaviour.** `t` replaces each `{name}` in the text with `String(params.name)`. A placeholder with no parameter is left as is.
- **Key names.** Keys are dotted, lower camel case, grouped by area, for example `tab.observe`, `admin.dialog.sign.title`, `admin.err.keyInSkill`.
- **Korean texts stay byte-identical.** Every existing Korean text moves to the catalog unchanged. The existing tests that match Korean strings must keep passing without edits, apart from imports.
- **Out of scope.** Texts generated by the engine (English) and by the observation service's English messages are not translated here.

### 2. Choosing the language

- **The stored setting.** `<userData>/settings.json` holds `{ "lang": "ko" | "en" }`.
  - Nothing else goes in this file.
  - It is written with `writeFileAtomic`, mode `0o600`.
  - A missing, unreadable or invalid file means no setting.
- **The language in effect** is the stored setting if there is one. Otherwise it is `langFromLocale(app.getLocale())`.
- **New IPC channels**, which follow the existing handler style and sender check:
  - `settings:get-lang`: no arguments; returns `Lang`.
  - `settings:set-lang`: `lang` must be exactly `'ko'` or `'en'`, otherwise the call is refused. It stores the setting and returns `Lang`.

  `RendererApi` gains `getLang(): Promise<Lang>` and `setLang(lang: Lang): Promise<Lang>`.
- **The switch.** The renderer shows a small switch in the header, `한국어 | English`. Changing it re-renders the whole page in the new language and sets `<html lang>`. The renderer's own state is kept: tabs, selections, and text the user has typed.
- **Main and service texts.** Native dialogs and session messages read the language at the moment they are built:
  - `main.ts` keeps a `currentLang` variable and passes `lang: () => currentLang` to `AdminSession`.
  - `AdminSessionOptions` gains `lang?: () => Lang`. The default is `() => 'ko'`, so existing tests are unchanged.

### 3. Dialog texts are testable

- **The builder module.** The native dialog contents move out of `main.ts` into a pure module, `gui/src/main/dialog-text.ts`. It exports one builder per dialog:
  - `reviewDialog(lang, summary)`, `signDialog(lang, summary)`, `resetDialog(lang)`, `keyPickerTitle(lang)`.
  - Any other dialog in `main.ts` gets a builder in the same way.
- **What a builder returns.** `{ title, message, detail, action }`, or the title string for pickers. It applies `dialogSafe` to every value it inserts, as today.
- **`main.ts`** calls these builders.

### 4. English wording

The English is written for administrators and must state the same facts as the Korean. Dialog texts on the review and signing path are security text: the English must not soften or drop a warning.

| Korean | English |
|---|---|
| 검토 / 검토함 | Review / Reviewed |
| 서명 | Sign |
| 승인자 | approver |
| 루트 관리자 | root administrator |
| 인증서 | certificate |
| 폐기 | revoke / revocation |
| 기록 초기화 | Reset memory |
| 키 불러오기 | Load key |
| 키 빼기 (disarm) | Unload key |
| 관리 (tab) | Admin |

Use plain sentences, with no exclamation marks. Errors say what happened and what to do.

### 5. Tests

**`gui/tests/i18n.test.ts` (new):**
- Both languages have exactly the same keys.
- Every text uses the same `{placeholders}` in both languages.
- No `en` text contains Hangul.
- `t` replaces placeholders.
- `langFromLocale` gives `ko-KR → ko`, `ko → ko`, `en-US → en`, `fr → en` and `undefined → en`.

**`gui/tests/dialog-text.test.ts` (new):**
- For each builder, the `ko` output equals the current Korean text exactly.
- The `en` output contains no Hangul and contains every inserted value: the digest, the key id and the reason.

**`gui/tests/admin.test.ts`:**
- One new test with `lang: () => 'en'`. Two session refusals (no key loaded, and the cooldown) come back in English.

**Settings:**
- A test for the settings read and write: a missing file, an invalid file, and a round trip.

### 6. Screenshots in the README

1. **Folder.** English screenshots go in `docs/images/`, PNG, taken at `deviceScaleFactor: 2` on a window of 1280×800.
2. **Data.** They use the GUI demo data (`node gui/scripts/demo.ts setup <dir> --org`), with `settings.json` set to `{"lang":"en"}` before launch.
3. **Shots:**
   - `gui-observe.png`: the observation tab with the Skill list and one Skill's detail;
   - `gui-admin-templates.png`: the admin tab's template picker;
   - `gui-admin-approve.png`: the Approve template chain with an approver key loaded (IDENTITY done) and INSPECT showing a Skill.
4. **Native dialogs** are not shot, because they are drawn by the OS outside the page.
5. **The script.** It is committed as `gui/scripts/screenshots.ts` and run with Playwright's Electron driver. It follows the existing smoke and demo scripts.
6. **`README.md`.** A short "Desktop GUI" section, near the existing GUI row in the tools table, shows the three images with one sentence each.
7. **`gui/README.md`** shows the same images and documents the language switch.
8. **Korean shots** are not added.
